# Code of Conduct

## Purpose

This Code of Conduct defines how contributors, maintainers, AI-assisted operators, and reviewers should collaborate in the AI Agent Library repository.

The goal is simple: keep the work useful, professional, scoped, safe, and reviewable.

This repo is meant to be an operating library for AI-agent assets — not a place for chaos goblins, drive-by drama, or PRs that arrive wearing a trench coat full of unrelated refactors. 🤝

## Who This Applies To

This Code of Conduct applies to:

- repository maintainers
- human contributors
- AI-assisted contributors
- Jules/Codex/ChatGPT-generated PRs
- issue commenters
- PR reviewers
- internal collaborators
- future community contributors

It applies in:

- GitHub issues
- pull requests
- reviews
- discussions
- comments
- commit messages
- documentation
- related project coordination spaces

## Expected Behavior

Contributors are expected to:

- be respectful and professional
- keep feedback focused on the work
- explain requested changes clearly
- keep PRs scoped to the approved task
- avoid personal attacks
- avoid harassment or intimidation
- avoid inflammatory language
- avoid spamming issues or PRs
- avoid knowingly submitting unsafe content
- disclose when content is AI-generated if relevant
- accept review feedback in good faith
- preserve public-safe and privacy-safe standards

## Repo-Specific Collaboration Standards

This repository values:

- clear file paths
- clear naming
- complete Markdown
- valid JSON
- minimal workflow permissions
- public-safe language
- synthetic examples
- small scoped PRs
- useful PR descriptions
- honest validation notes
- clear separation of current work and future work

## Unacceptable Behavior

Unacceptable behavior includes:

- harassment
- threats
- insults
- personal attacks
- discriminatory language
- sexualized comments or imagery
- intimidation
- doxxing
- spam
- malicious edits
- intentionally introducing secrets
- intentionally exposing private data
- knowingly adding fake testimonials
- knowingly adding unsupported outcome promises
- bypassing review
- misrepresenting validation or test results
- repeatedly ignoring maintainer scope instructions

## AI-Assisted Contribution Standards

AI-generated or AI-assisted work must still meet repo standards.

AI-assisted contributors must not:

- invent facts
- invent URLs
- invent citations
- invent partner relationships
- invent testimonials
- invent repo files
- invent validation results
- expose private material
- include real customer data
- include secrets
- skip review

AI output should be treated as a draft until reviewed.

## Issue Behavior

Good issues are:

- specific
- scoped
- actionable
- tied to files or outcomes
- clear about acceptance criteria
- clear about out-of-scope work

Good issue title examples:

```text
[Skill]: Add static site section library builder
[Repo Maintenance]: Normalize template index slugs
[Bug]: Fix broken site-data navigation path
[Feature]: Add platform README for n8n
```

Poor issue title examples:

```text
stuff
fix all
more pages
bad
updates
```

## Pull Request Behavior

Good PRs:

- link the issue or batch
- change only expected files
- include a useful summary
- list validation performed
- call out known issues
- avoid unrelated refactors
- avoid future-batch work
- avoid deployment changes unless approved

Bad PRs:

- hide unrelated edits
- rewrite broad files without need
- include secrets
- include private data
- claim validation that was not done
- mix multiple issues together
- introduce frameworks or package managers without approval

## Review Behavior

Good reviews:

- focus on the code/content
- identify specific files or sections
- explain why a change is needed
- distinguish blockers from suggestions
- call out safety/privacy issues clearly
- keep feedback professional
- approve only when scope and safety are acceptable

Reviewers should avoid:

- vague criticism
- personal attacks
- sarcasm aimed at people
- demanding unrelated work inside the current PR
- using review comments to expand scope

## Maintainer Standards

Maintainers should:

- enforce scope
- protect repo safety
- require validation
- request changes when needed
- avoid merging risky PRs
- separate future work into future issues
- keep feedback direct and fair
- resolve conflict discussions professionally
- prioritize repo integrity over speed

## Contributor Standards

Contributors should:

- read the relevant docs before editing
- follow issue scope
- use repo-relative paths
- use lowercase kebab-case naming
- validate changed files
- disclose known limitations
- ask for clarification when scope is unclear
- avoid committing generated junk
- avoid committing local machine paths
- avoid committing private or sensitive data

## Handling Disagreements

When disagreement happens:

1. Return to the issue objective.
2. Identify the exact file or behavior in dispute.
3. Separate blockers from preferences.
4. Keep comments focused on merge readiness.
5. Create a follow-up issue for broader ideas.
6. Ask a maintainer to decide if needed.

Do not turn a narrow PR into a philosophical cage match.

## Reporting Conduct Problems

Report conduct problems to the repository maintainer through an appropriate private channel when possible.

Public reports should avoid exposing private personal information.

If a conduct issue also involves a security issue, follow `SECURITY.md`.

## Enforcement Options

Maintainers may take any of the following actions:

- ask for clarification
- edit or remove comments where supported
- request changes
- close an issue
- close a PR
- limit participation
- block a contributor where appropriate
- escalate to platform-level reporting if needed

Enforcement should be proportional to the issue.

## Safety Overrides

Maintainers may immediately block or close work that:

- exposes secrets
- exposes private data
- includes abusive content
- includes malicious code
- attempts to bypass review
- adds unsafe public claims
- creates serious repo or user risk

## Public-Safe Communication

For funding, finance, credit, legal, tax, business, or AI automation topics, use careful language.

Use:

```text
educational
planning
readiness
possible fit
compare options
review required
terms vary
human review recommended
```

Avoid:

```text
guaranteed approval
guaranteed funding
guaranteed credit improvement
guaranteed income
guaranteed ranking
fix your credit
bypass underwriting
```

## Review Checklist

Before participating, contributors should confirm:

- [ ] I understand the task scope.
- [ ] I will keep comments professional.
- [ ] I will not include private data.
- [ ] I will not include secrets.
- [ ] I will not invent facts, URLs, or validation results.
- [ ] I will keep PRs scoped.
- [ ] I will accept review feedback in good faith.

## Done Means

Healthy repo collaboration means:

- issues are clear
- PRs are scoped
- reviews are specific
- maintainers enforce standards fairly
- contributors protect privacy and safety
- future work is separated into future issues
- people can improve the repo without stepping into a swamp
