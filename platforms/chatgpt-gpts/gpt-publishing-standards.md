# GPT Publishing Standards

Use these standards before promoting a Custom GPT publicly or sharing it with partners.

## Naming

- Use clear outcome-driven names.
- Avoid backend provider names in public GPT names unless explicitly approved.
- Prefer stable names that can survive platform migration.
- Avoid jokes that obscure the actual use case.

## Descriptions

A strong GPT description should explain:

- who it helps
- what problem it solves
- what output it creates
- when not to use it

## Visibility

Every GPT must have one visibility level:

- `public` — safe for public directory, lead magnets, or marketing pages
- `partner-facing` — safe for approved partners, not necessarily public SEO
- `internal-only` — contains ops logic, CRM logic, routing logic, sensitive workflows, or provider risk
- `archive` — duplicate, stale, unclear, or not worth promoting

## Links

- Prefer canonical ChatGPT access URLs.
- Do not publish editor URLs as public links.
- Check links quarterly.
- If a URL is missing, mark it `Unknown` rather than inventing it.

## Profile images

- Preserve profile image URLs in source data if they are part of the export.
- Do not rely on signed image URLs for long-term public rendering.
- For public site use, replace unstable signed URLs with durable hosted assets later.

## Safe public presentation

Public pages must not include:

- private client data
- secrets, tokens, or API keys
- backend-provider bypass paths
- funding approval guarantees
- legal, tax, credit repair, or financial advice claims
- internal-only routing logic

## Update cadence

Review promoted GPTs quarterly for:

- broken links
- outdated positioning
- stale knowledge files
- duplicate use cases
- monetization opportunities
- visibility mismatches
